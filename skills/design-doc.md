# Design a change

Use the system knowledge given (architecture, risks) and read the code it points to.

## Output (one page)
1. **Goal**: the problem and how we'll know it is solved (acceptance criteria as testable statements).
2. **Approach**: the components and files to change, and why this way. Name one alternative and why not.
3. **Data**: new or changed data, especially personal data (purpose, retention, access).
4. **Risks**: security, privacy, compatibility, performance; mitigations.
5. **Test plan**: unit, integration and manual checks that prove each acceptance criterion.
6. **Rollout**: flags, migrations, how to roll back.
